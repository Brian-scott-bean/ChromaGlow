## 1. Executive summary

ChromaGlow is, on balance, a carefully engineered local-first smart-home controller. There is **no Critical finding and no remote-exploitable vulnerability.** Credentials are treated as local-only secrets that never touch a backend; the sensitive DTLS pre-shared key is kept out of the App Group / WCSession sharing paths; the real-time REST paths use a latest-wins mailbox with batching and delta-skip to respect the bridge's throttling; and — most impressively — the **Android** pairing TLS stack (Batch 3/4) is a textbook implementation: pinned Signify roots with no system fallback, fail-closed chain validation, strict uppercase-16-hex bridgeid CN extraction with an RFC 2253-aware DN parser, and belt-and-suspenders GET→POST identity continuity (D-014). That Android design is the reference the iOS transport should be measured against.

The dominant theme across the confirmed defects is **iOS transport authentication and credential-in-logs hygiene.** iOS talks to the bridge over trust-all TLS on *every* surface (main app, SSE, widget, Siri intents, watch): the delegate either never evaluates the certificate or evaluates it and discards the result, then unconditionally returns `.useCredential`. Because those same connections carry the `hue-application-key` bearer header — and, for the v1 client, the token embedded directly in the URL path that is then logged at `privacy: .public` — a LAN man-in-the-middle can capture full local bridge-control credentials. Separately, the successful-pairing response (bridge application key **and** entertainment client key) is written verbatim to the unified log at `.public` in release builds. None of this is remotely exploitable and the blast radius is local light control, but it directly violates the project's own written rules ("Never log tokens/keys"; "Never implement trust-all TLS") and is the correct top priority.

The second theme is **reliability of the flagship real-time features.** Several confirmed medium defects can silently break bridge-stored animations, Composer/Studio entertainment sessions, and bulk automations on realistic homes: a background refresh can tear down the app's own active DTLS session; multi-bridge composition teardown targets the wrong bridge; bridge-stored rules overflow the v1 8-actions-per-rule limit for any 8+ light room; per-light v1 IDs are mapped by position rather than identity; and "All Off"/automation bursts fire unthrottled and drop commands. There is also a genuine data-loss path: a single unreadable element in `compositions.json` (made likely by non-migration-safe sub-config Codable) triggers a destructive reseed that overwrites the user's entire saved library.

Finally, there is one **App Store release blocker**: the widget and watch bundles use the UserDefaults required-reason API but ship without their own `PrivacyInfo.xcprivacy`, which will trip ITMS-91053 at upload. This is cheap to fix and should be treated as P0 alongside the log-scrubbing changes.

### HIGH

#### H-01 — [iOS] Systemic trust-all TLS on the main-app data plane (SSE + v1/v2 REST bearing the app key)
**File:** `HueHome/Core/Network/HueAPIClient.swift:722` (verdict: CONFIRMED)
**Merges:** the trust-all delegate as reported under `ios-transport` (high), `ios-network` (medium), and `x-secrets-sweep` (medium) — same `HueCertTrustDelegate`, same defect.

- **Defect:** `HueCertTrustDelegate.acceptBridgeCert` calls `SecTrustEvaluateWithError(serverTrust, &cfError)` and then **discards the boolean** (`_ = …`, line 722), unconditionally returning `completionHandler(.useCredential, URLCredential(trust: serverTrust))` (line 723) for every server-trust challenge. No pinning, no leaf-CN==bridgeid check, no chain-validation gating. This one delegate instance backs the v2 client (`:63`), the SSE service (`HueSSEService.swift:62`), the v1 client (`:56`), and the orchestrator SSE session (`UnifiedOrchestrator.swift:329`) — i.e. *all* bridge traffic, including the SSE stream that sends `hue-application-key: <token>` (`HueSSEService.swift:93`).
- **Failure scenario:** An attacker on the same LAN ARP-spoofs the bridge IP and presents any self-signed cert. The delegate accepts it; the app sends its bearer app key to the attacker (and, for v1, the token in the URL). The attacker gains full local Hue control and can inject arbitrary bridge responses. No warning surfaced.
- **Fix:** Pin the bridge certificate/public-key SPKI captured at pairing (store in Keychain, compare in the delegate), or at minimum require the self-signed leaf CN to equal the canonical uppercase-16-hex bridgeid. Only return `.useCredential` when evaluation succeeds against an anchor set that includes the pinned cert; otherwise `.cancelAuthenticationChallenge`. Mirror the Android `HueRootTrustManager` + `HueLeafHostnameVerifier` design. Route this through the deferred **D-001 TLS-bootstrap** decision.

#### H-02 — [iOS] Trust-all TLS during bridge pairing / credential provisioning
**File:** `HueHome/Core/ViewModels/BridgeDiscoveryViewModel.swift:78` (verdict: PLAUSIBLE — real defect, severity corrected from "critical" to high)
**Merges:** the same delegate reported under `ios-discovery-pairing` (high) and `ios-concurrency` (medium).

- **Defect:** `BridgeCertTrustDelegate.urlSession(_:didReceive:completionHandler:)` returns `.useCredential` for any server-trust challenge (line 78) with zero validation — never calls `SecTrustEvaluateWithError`, never pins the Signify CA, never checks leaf CN vs bridgeid, never confirms the peer is on the local subnet. It is installed for every HTTPS pairing POST (port 443) at lines 312–315, and that POST persists the returned application key + entertainment client key to Keychain (lines 359–375).
- **Failure scenario:** A LAN attacker (rogue AP, ARP spoof, spoofed `_hue._tcp` mDNS / NUPnP `internalipaddress`) MITMs the pairing exchange during the user-initiated pairing window. They relay to the real bridge and capture the freshly minted credentials, or impersonate the bridge and return an attacker-chosen `username` that the app then persists — connecting the app to attacker infrastructure at provisioning time.
- **Fix:** After the handshake, `SecTrustEvaluateWithError` and verify the leaf CN equals the uppercase-16-hex bridgeid returned by `/api/0/config` only after chain validation succeeds; fall back to `performDefaultHandling`. Never return `.useCredential` without evaluating trust. (Note: Hue bridges use self-signed certs, so the durable fix is TOFU/SPKI pinning + bridgeid-CN verification, consistent with the Android identity contract.)

#### H-03 — [iOS] Hue v1 application key logged in cleartext via request URLs (`privacy: .public`, release builds)
**File:** `HueHome/Core/Network/HueV1Client.swift:439` (verdict: CONFIRMED)
**Merges:** identical finding reported under `ios-network` and `x-secrets-sweep`.

- **Defect:** The v1 REST endpoint carries the app key **in the URL path**: `baseURL = "https://\(ip)/api/\(token)"` (line 70). Every helper logs the full URL with a forced `privacy: .public` that defeats os_log redaction — `V1 GET` (439), `POST` (452), `PUT` (465), `DELETE` (476) — and `execute()` additionally logs `request.url?.path` (`/api/{token}/…`) at `.public` (line 483). None are `#if DEBUG`-gated, so they run in Release. (v2 is safe: v2 keeps the token in the `hue-application-key` header, not the URL.) `HueV1Client` is exercised by real flows: `BridgeAnimationEngine` rule/schedule uploads and Settings "clean bridge"/purge.
- **Failure scenario:** User runs any bridge-stored animation; the OS writes e.g. `V1 PUT https://192.168.1.42/api/<40-char-appKey>/schedules` to the unified log. Anyone who captures a sysdiagnose (routinely attached to support tickets) or attaches the device to Console.app reads the plaintext application key and takes full local control.
- **Fix:** Never log the v1 URL/path. Log only method + resource type + status (`V1 PUT /schedules -> 200`); strip the `/api/{token}` segment; drop `privacy: .public` from anything derived from `baseURL`/`request.url`/IP. Prefer default `.private` redaction for all interpolated network strings.

#### H-04 — [iOS] Pairing bridge token + entertainment client key written to logs
**File:** `HueHome/Core/ViewModels/BridgeDiscoveryViewModel.swift:332` (verdict: CONFIRMED)
**Merges:** the unified-log leak (`ios-concurrency` high / `ios-discovery-pairing` medium) **and** the in-memory/DEBUG-UI `appendLog` leak at lines 363/365 (`ios-discovery-pairing` medium, `ios-transport` low, `x-secrets-sweep` low). Two related mechanisms, one root cause: secrets in pairing logs.

- **Defect (primary, release):** `log.info("Pairing: Raw response: \(raw, privacy: .public)")` (line 332) is **not** `#if DEBUG`-gated. On success, `raw` is `[{"success":{"username":"<APP_KEY>","clientkey":"<ENT_KEY>"}}]`, so the application key and entertainment client key are written verbatim to the unified log in all builds. (`.info` lives in the in-memory ring buffer but is still captured by sysdiagnose and live Console.)
- **Defect (secondary, DEBUG-scoped):** `appendLog("✅ Paired! Application Key: \(token)")` (363) and `appendLog("🔑 Client Key (Entertainment): \(clientKey)")` (365) interpolate both secrets into `logLines`, which is appended unconditionally (408). The on-screen debug-log UI (`BridgeSetupView.swift:595`) and the `print(line)` are `#if DEBUG`-only, so in Release the secrets persist only in-memory (no display/export path today); in DEBUG/internal builds they render on screen (screenshot/screen-share leak).
- **Failure scenario:** A shipping build leaks the app key + entertainment PSK to any sysdiagnose/Console capture; an internal build shows both secrets on screen during pairing.
- **Fix:** Remove the raw-response `.public` log (line 332) and delete lines 363/365. Log only non-secret metadata (`token.count`, as line 367 already does correctly). Never interpolate `token`/`clientKey` into any log sink in any build. The safe pattern already exists in the same file — apply it consistently.

### MEDIUM

#### M-01 — [iOS] Trust-all TLS on ancillary token-bearing surfaces (widget read + widget intents + Siri intents + watch)
**File:** `HueHomeWidget/WidgetIntents.swift:45` (verdict: PLAUSIBLE)
**Merges:** `WidgetDataStore.swift:205`, `WidgetIntents.swift:45` (×2 dimensions), `HueIntentAPIClient.swift:69`, `LightShadeWatchApp Watch App/WatchStore.swift:262` — the same trust-all pattern as H-01 replicated on every extension/watch surface.

- **Defect:** `WidgetAPIClient.TrustDelegate`, `BridgeWriter.TrustAll`, `HueIntentAPIClient.TrustDelegate`, and `WatchStore.TrustAll` all return `URLCredential(trust:)` for any server-trust challenge with no validation; each transmits the token via the `hue-application-key` header (widget timeline fetch, `ToggleRoom/ApplyPreset/AllOff` PUTs, Siri `ToggleRoom/SetBrightness`, watch toggle/brightness/preset/all-off).
- **Failure scenario:** A LAN MITM captures the token when the user taps a widget button, invokes Siri, or controls from the watch — including from background extensions the user cannot see.
- **Fix:** Share **one** pinned-trust evaluator (the H-01 solution) across the app, widget, intents, and watch targets; reject on mismatch. Do not maintain per-target trust-all delegates. (Propagate the pin to the watch via WCSession alongside credentials.)

#### M-02 — [iOS] Bridge token persisted in plaintext App Group UserDefaults and watch UserDefaults
**File:** `HueHome/Core/Network/WidgetDataStore.swift:84` (verdict: PLAUSIBLE / CONFIRMED mechanism)
**Merges:** `WidgetDataStore.swift:84/82` (App Group), `WatchStore.swift:302/303` (watch `UserDefaults.standard` + App Group mirror).

- **Defect:** `write(ip:token:)` / `write(bridges:)` serialize the raw token (and per-bridge `WidgetBridgeCredentials.token`, a plaintext Codable `String`) into the `group.com.huehome.pro` suite; the watch stores the token in `UserDefaults.standard("wc_token")` and mirrors it into the App Group. The authoritative iOS copy is correctly in Keychain (`WhenUnlockedThisDeviceOnly`), but these are unencrypted plists readable by any process in the app group and included in unencrypted local backups. The watch has **no Keychain at all**. AGENTS.md flags this as a known risk not to be treated as acceptable.
- **Failure scenario:** An unencrypted local backup, jailbroken/lost-device filesystem access, or any future extension added to the app group recovers the plaintext token for every paired bridge, bypassing the Keychain protections. (Low-value LAN-only token; requires local/backup access — hence medium, not high.)
- **Fix:** Stop writing tokens to UserDefaults. Share credentials via a **Keychain access group** (`kSecAttrAccessGroup`, `AfterFirstUnlockThisDeviceOnly`) so widget/watch/intents read from Keychain. If a shared cache is unavoidable short-term, store only non-secret routing metadata there and fetch the token from Keychain at use time; on watchOS use a watch Keychain.

#### M-03 — [iOS] Widget & watch extensions ship without a PrivacyInfo.xcprivacy despite using the required-reason UserDefaults API (App Store blocker)
**File:** `LightShadeWatch/WatchWidgetStore.swift:31` (verdict: CONFIRMED)

- **Defect:** Only the main `HueHome` target bundles `PrivacyInfo.xcprivacy`. The `HueHomeWidgetExtension`, `LightShadeWatchExtension`, and `LightShadeWatchApp Watch App` Resources phases are empty, and none of those folders contains a manifest, yet all three binaries call `UserDefaults(suiteName:)`/`UserDefaults.standard` (`NSPrivacyAccessedAPICategoryUserDefaults`, declared as CA92.1 only in the app target). Privacy manifests are per-bundle and not inherited.
- **Failure scenario:** App Store upload triggers **ITMS-91053 "Missing API declaration"** for the widget/watch bundles, blocking release.
- **Fix:** Add a `PrivacyInfo.xcprivacy` to each extension/watch-app target declaring `NSPrivacyAccessedAPICategoryUserDefaults` reason CA92.1 (matching the app), and add them to those targets' Resources build phases.

#### M-04 — [iOS] `resolveV1LightIDs` maps colors to lights by position; the uniqueid mapping is dead code
**File:** `HueHome/Core/Network/HueV1Client.swift:403` (verdict: CONFIRMED)

- **Defect:** The resolver builds `uniqueIDToV1ID`/`v2ToV1` (393–398) but never reads them; it returns `Array(v1Lights.keys).sorted{numeric}.prefix(count)` — i.e. the numerically-lowest N lights on the **entire bridge** (`fetchLights()` is unscoped), ignoring the v2 channel/UUID order and room membership.
- **Failure scenario:** For a bridge-stored animation, each frame's per-light color is written to the wrong physical bulb, or to bulbs outside the room entirely (in a multi-room home the lowest-numbered bridge lights animate while room bulbs stay dark). The `.static` per-light palette gradient makes ordering load-bearing, so this genuinely scrambles output.
- **Fix:** Use `light.id_v1` ("/lights/N") from the v2 light objects to build a deterministic v2-UUID→v1-numeric map; pass the v2 light objects into the resolver; delete the unused `uniqueIDToV1ID` block. Never fall back to positional guessing.

#### M-05 — [iOS] Bridge-stored rule actions exceed the v1 8-actions-per-rule limit for rooms with 8+ lights
**File:** `HueHome/Core/Network/BridgeAnimationEngine.swift:214` (verdict: CONFIRMED)

- **Defect:** Each step-rule appends one PUT action per light (214–221) plus a sensor-advance action, but light count is only capped at 20, never at the v1 rule limit. The code's own comment ("Max 8 actions per rule … Safe for up to 7 lights") is unenforced: 8+ lights → 9+ actions → `createRule` throws → the whole upload aborts.
- **Failure scenario:** A user with a common 8+ bulb room taps a bridge-eligible preset; rule creation fails, upload throws, the feature silently falls back to app-driven (`UnifiedOrchestrator.swift:1881–1885`), and "close the app, lights keep running" never works for any normal-sized room. Orphaned `CG_` resources leak until the next purge.
- **Fix:** Cap lights-per-rule to 7 (or split a step across chained rules), or drive lights via scene activation so a step is one action; validate action count before POSTing and chunk accordingly.

#### M-06 — [iOS] `deactivateStuckEntertainmentSessions` runs on every `loadAll` and can kill the app's own active DTLS session
**File:** `HueHome/Core/Network/UnifiedOrchestrator.swift:3049` (verdict: CONFIRMED)

- **Defect:** `loadAll()` always runs `deactivateStuckEntertainmentSessions` concurrently with the bridge fetch (627). That routine POSTs `action:stop` to **every** `entertainment_configuration` with `status=="active"` (3046–3058), with no ownership or age check. The app's own Studio/Composer session is `active` (`startSession` → `action=start`), and `loadAll` is invoked from launch, DashboardView `.task`/scenePhase→active, and `scheduleStateRefresh()` 1.5s after any toggle/brightness.
- **Failure scenario:** During a Composer/strobe/party effect, an everyday lock/unlock (scenePhase→active) or a room toggle triggers `loadAll`, which stops the running config. The composition loop keeps calling `entClient.send()` into a dead session (no reconnect) — lights freeze mid-show.
- **Fix:** Exclude configs the app is actively streaming (track active configID per bridge in `studioEntClients`/`compositionEntRoomByBridge`), or only deactivate sessions older than a threshold / not owned by this app. Do not run this cleanup while a local entertainment session is active.

#### M-07 — [iOS] `stopCompositionMode` tears down bridge animation via `primaryAPIClient` — wrong bridge in multi-bridge setups
**File:** `HueHome/Core/Network/UnifiedOrchestrator.swift:2013` (verdict: CONFIRMED)

- **Defect:** Stop builds its v1 client from `primaryAPIClient` (= `clients.values.first`, unordered), not the bridge the animation lives on. `startCompositionMode` correctly used `hueClient(for: room.bridgeID)`; the manifest carries `bridgeIP`. `bridgeAnimationStore.remove` runs unconditionally regardless of whether deletes reached the right bridge.
- **Failure scenario:** With two bridges, a bridge-stored animation on bridge B (not first) is torn down against bridge A (404/no-op) while B keeps looping forever, and the manifest is dropped locally so the app can no longer clean it up.
- **Fix:** Resolve the client from the manifest's bridge (match `manifest.bridgeIP`, or store `bridgeID` in the manifest and use `hueClient(for:)`); only remove the manifest after the correct-bridge deletes succeed.

#### M-08 — [iOS] Bulk `grouped_light` writes fire N concurrent PUTs with no staggering; commands silently dropped on larger homes
**File:** `HueHome/Core/Network/UnifiedOrchestrator.swift:930` (verdict: CONFIRMED)

- **Defect:** `applyAutomationPreset` (925–942), `applyAutomationEffect` (959–992), and `turnAllOff` (1015–1025) add one task per room to a `withTaskGroup` and fire all `grouped_light` PUTs simultaneously with no batch/stagger/mailbox/retry; errors are swallowed with `try?`. The codebase's own comments elsewhere note the bridge accepts ~7 simultaneous PUTs before throttling and "silently drops excess," and the sibling per-light paths implement batching that these paths bypass.
- **Failure scenario:** A home with ~8+ rooms triggers a preset or All Off; several PUTs get 429/503, are dropped, and those rooms silently stay in their old state (All Off leaves lights on). The optimistic UI is not reconciled until the next periodic `loadAll` (~120s), with no toast/retry.
- **Fix:** Route these bursts through a shared per-bridge rate limiter/mailbox (as the Sync/Studio paths do), chunk with a small delay, and surface/retry failures instead of swallowing them.

#### M-09 — [iOS] Data race on `resumed` can double-resume the DTLS handshake continuation (crash)
**File:** `HueHome/Core/Network/HueEntertainmentClient.swift:214` (verdict: PLAUSIBLE)

- **Defect:** `openDTLSConnection` guards a checked continuation with `nonisolated(unsafe) var resumed`, read/written from two different queues (state handler on `.global(qos:.userInteractive)`, timeout on default `.global()`) with no lock/atomic. `nonisolated(unsafe)` disables race checking; both paths can observe `resumed == false` and both call `continuation.resume()`.
- **Failure scenario:** On a congested LAN the handshake completes/fails near the 10s mark concurrently with the timeout; both resume the continuation → `SWIFT TASK CONTINUATION MISUSE` hard trap. (Narrow window → medium, not high.)
- **Fix:** Guard `resumed` with an actor-isolated `finishOnce()` helper, `OSAllocatedUnfairLock`, or an atomic compare-and-set so only one path resumes.

#### M-10 — [iOS] DTLS send failure marks state `.error` but never cancels the connection or recovers
**File:** `HueHome/Core/Network/HueEntertainmentClient.swift:274` (verdict: CONFIRMED)

- **Defect:** `handleSendError` only sets `state = .error` and logs — no `connection.cancel()`, no nil-out, no reconnect, no propagation. Because `send()` guards on `case .streaming`, every subsequent frame silently no-ops; `state` is never read by callers, and the `SyncModeEngine` watchdog covers only REST, not the DTLS transport.
- **Failure scenario:** A transient UDP error during music sync flips state to `.error`; the engine keeps calling `send()` at 25–50fps, all frames drop, and the lights freeze on their last frame for the rest of the session with no user feedback and no fallback to REST.
- **Fix:** In `handleSendError`, cancel + nil the connection and either drive a bounded reconnect (re-run `openDTLSConnection`) or propagate the error so the caller can fall back to REST, matching `SyncModeEngine.startEntertainmentIfAvailable`.

#### M-11 — [iOS] NUPnP 12s fallback overrides / discards mDNS results the user is already choosing from
**File:** `HueHome/Core/ViewModels/BridgeDiscoveryViewModel.swift:214` (verdict: CONFIRMED)

- **Defect:** The scan-timeout task guards only on `case .scanning`, but the design intentionally stays `.scanning` while mDNS results accumulate in `discoveredBridgeChoices`. So after 12s the NUPnP fallback runs even when mDNS already found bridges: an empty NUPnP result calls `handleError` (→ `.error`, wiping the chooser), a non-empty result force-selects `.bridgeFound(nupnpBridge)`.
- **Failure scenario:** User sees two locally-discovered bridges; 12s later NUPnP returns `[]` (cloud offline/rate-limited) and the user is bounced to "Something went wrong," or NUPnP returns only bridge A and the app hides bridge B the user intended to pick.
- **Fix:** `guard discoveredBridgeChoices.isEmpty else { return }` before starting the NUPnP fallback and before acting on its result. Never let a cloud-fallback empty result drive `handleError` or replace an existing local selection.

#### M-12 — [iOS] One-shot location manager can be deallocated across `await`, hanging the "Set location" flow forever
**File:** `HueHome/UI/Settings/SettingsView.swift:750` (verdict: PLAUSIBLE)

- **Defect:** In `OneShotLocation.request()`, `mgr` (CLLocationManager) and `delegate` are function-local `let`s. `CLLocationManager.delegate` is weak, so the only strong owners are locals captured by the non-escaping continuation-body closure. After the closure runs and the function suspends at `await`, ARC in an optimized build may release both; the manager tears down before any callback fires and the checked continuation is never resumed. No timeout.
- **Failure scenario:** Settings → All Day Scenes → "Set": on a release build the manager is deallocated after suspend, no callback arrives, `requestOneTimeLocation()` never returns, `isRequestingLocation` stays true, the button spins indefinitely, and the circadian anchor can never be set. (Optimizer-dependent → PLAUSIBLE.)
- **Fix:** Keep the manager + delegate alive for the request's lifetime (store as properties, `withExtendedLifetime`, or have the delegate strongly retain the manager until the continuation resumes) and resume with a timeout so the UI can't hang.

#### M-13 — [iOS] Composition library data-loss: destructive reseed on any decode failure, made likely by non-migration-safe sub-config Codable
**File:** `HueHome/Core/Models/CompositionStore.swift:102` (verdict: PLAUSIBLE)
**Merges:** the destructive `load()` path (`CompositionStore.swift:102`) with its most common trigger — synthesized Codable on the Composer sub-configs (`CompositionModels.swift:122`, CONFIRMED).

- **Defect:** `load()` decodes the whole file as `[CompositionPreset]` in one shot; any decode error is swallowed by a catch that sets `presets = builtInPresets` and immediately `persist()`s the defaults over `compositions.json` (`.atomic`, no backup). The decode is fragile because `PaletteConfig/MotionConfig/EnvelopeConfig/ReactionConfig/CodableColor` rely on **synthesized** Codable, which throws `keyNotFound` for missing non-optional keys (e.g. `MotionConfig.motionAngle`, added after the original schema per git). `CompositionPreset.init(from:)` uses `decodeIfPresent` for its own top-level late-added fields but delegates the nested configs via plain `container.decode`, so a nested throw propagates.
- **Failure scenario:** A composition saved by an earlier build (before a sub-config field existed) is loaded by the current build on a routine app update; the whole `[CompositionPreset]` decode throws, the catch reseeds to built-ins and overwrites the file — every user-created composition is permanently gone. (`.atomic` writes and absence of file-sharing rule out some triggers, so PLAUSIBLE, but the schema-drift trigger is already realized in git history.)
- **Fix:** In the catch, **never** call `persist()` (do not overwrite the source on a read failure). Decode elements leniently (array of `FailableDecodable<CompositionPreset>`, keep the good ones), and give each sub-config an explicit `init(from:)` using `decodeIfPresent` + struct defaults for every non-optional field (or make new fields optional), mirroring the migration-safety already applied at the top level. Write a timestamped `.bak` before any recovery reseed.

- **L-01 [iOS] Optimistic SSE guard cleared at PUT completion instead of the intended 1.5s** — `UnifiedOrchestrator.swift:760` (CONFIRMED). (Narrow: most logical failures already arrive as non-2xx.)
- **L-03 [iOS] Data race on lazy `session` under concurrent first access** — `HueAPIClient.swift:64` (PLAUSIBLE). `@unchecked Sendable class` with `private lazy var session`; parallel per-bridge fetches + `deactivateStuck` first-touch the same client's `session` concurrently. - **L-04 [iOS] Bridge capacity check requires free scenes the rules-chain path never uses** — `HueV1Client.swift:36` (CONFIRMED). `canFitOneAnimation` requires `scenesAvailable >= 10`, but the current upload creates zero scenes (states embedded in rule actions). ## 4. Already solid (verified-good hardening — preserve these)

These were positively verified and should be protected with regression guards, not "fixed."

**Credentials & storage**
- **Keychain accessibility (iOS).** All Keychain writes use `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` (`KeychainManager.swift:182`, the sole `SecItemAdd`) — non-syncable (no iCloud), excluded from encrypted backup/new-device restore, unlock-gated. No weaker/syncable class exists anywhere. (Reported twice; merged.)
- **Entertainment client key kept Keychain-only (iOS).** The DTLS PSK is stored/loaded only via Keychain (`KeychainManager.swift:118`) and is structurally excluded from `WidgetBridgeCredentials`, App Group UserDefaults, and the WCSession payload (those carry only ip+token). The most sensitive streaming secret avoids the plaintext path that affects the token.
- **Bridge removal revokes secrets (iOS).** `BridgeManagerView.delete` → `orchestrator.removeBridge` → `keychain.deleteCredentials(for:)` wipes namespaced ip/token/clientKey and warns the user (`BridgeManagerView.swift:171`). (Only the L-15 abandoned-legacy-slot case escapes this.)
- **Android credential store (PENDING Batch 4).** Tokens are AES-256-GCM encrypted under a per-bridge non-exportable AndroidKeyStore key, written atomically (temp file + `ATOMIC_MOVE` + fsync) under `noBackupFilesDir/credentials` with `NOFOLLOW_LINKS` symlink guards, bounded blob sizes, and key/blob consistency checks (`AndroidKeystoreBridgeCredentialStore.kt:252`). Registry metadata persists only bridgeId/name/host/port/isActive — never secrets.

**Transport & TLS**
- **Android TLS is the reference implementation (Batch 3/4).** `HueRootTrustManager` (`:33`) anchors to exactly the two bundled Signify roots in a fresh `KeyStore(null,null)` with **no system/user fallback**, refuses an empty anchor set, requires exactly one X509TrustManager, and fails closed on self-signed/expired/foreign-CA leaves. `HueBridgeCommonName.extract` (`:58`) enforces exactly-one-CN, strict `^[0-9A-Fa-f]{16}$`, uppercase normalization. `Rfc2253DistinguishedName.parse` (`:46`) is escaping/quoting-aware, preventing embedded-CN confusion. `OkHttpHuePairingClient` (`:259`) wires the pinned factory + a hostname verifier that never returns blanket true. **GET→POST identity continuity (D-014, `:116`)** pins the POST leg to the GET-authenticated bridgeid and re-extracts/re-verifies the POST leaf. This is the model the iOS transport (H-01/H-02/M-01) should adopt.
- **DTLS transport hardening (iOS).** `HueEntertainmentClient` pins min=max TLS to DTLS 1.2, explicitly appends `TLS_PSK_WITH_AES_128_GCM_SHA256`, sources the PSK from Keychain, copies PSK bytes via `DispatchData(bytes:)`, and never logs the client key within the file (`:188`).
- **Entertainment config discovery is local-first (iOS).** `EntertainmentConfigManager`/builder talk only to the bridge over local CLIP v2, token header-only, defensive parsing, 10-light cap; no cloud dependency (`:18`).
- **Local-first discovery with validated cloud fallback (iOS).** mDNS `_hue._tcp` is primary; NUPnP is a timed, skippable fallback using `URLSession.shared` with **full ATS validation** (the trust-all delegate is confined to LAN pairing and never applied to the cloud call) (`BridgeDiscoveryViewModel.swift:200`).

**Concurrency & throughput**
- **RestSender latest-wins mailbox (iOS).** Bounds bridge write depth (~1 in-flight + 1 pending) and is used consistently by Sync/Composer/Studio REST paths, preventing unbounded backlog (`SyncModeEngine.swift:46`). (A minor `isInflight` race can transiently allow 2 in-flight, but it is bounded/self-correcting — worth tightening, see tests.)
- **Per-light REST batched/staggered/delta-skipped (iOS).** ≤5 concurrent PUTs per batch, 80ms inter-batch gap, delta-skip below thresholds, 20-light cap (`UnifiedOrchestrator.swift:2147`). (Contrast with M-08, which bypasses all of this.)

**Privacy / logging discipline (where it's done right)**
- **Raw bridge-response logging is DEBUG-only (iOS).** `logRaw` (full JSON incl. room/scene names) is wrapped in `#if DEBUG` (`HueAPIClient.swift:687`); the general decode-error log records only `error.localizedDescription`. (Info nit: even in DEBUG it uses `.public` on names — see roadmap P2.)

*(Several Android items — RFC 2253 unescape single-byte limitation, root-CA fingerprint verified only in the instrumented suite, TLS `ConnectionSpec`/CLEARTEXT not explicitly pinned, TOFU `expectedBridgeId=null`, blocking `pair()` not cancellable, `replacesbridgeid`/token-length/registry-lenient-decode/alias-validator, `allowBackup=true` with placeholder rules — verified as accurate but info-level hardening opportunities rather than defects; folded into the P2 roadmap below.)*

## 6. Recommended new tests / regression guards

Each fix should ship with a guard so it can't silently regress.

**TLS / trust (H-01, H-02, M-01)**
- iOS delegate unit/integration test: a self-signed leaf with a **mismatched CN** is rejected (`.cancelAuthenticationChallenge`); a leaf whose CN==bridgeid (or matching pinned SPKI) is accepted. Mirror the Android `HueRootTrustManagerTest`/`HueLeafHostnameVerifierTest` cases (empty anchors, untrusted CA, self-signed, expired, foreign bridgeid, GET→POST identity swap).
- A test asserting the delegate **never returns `.useCredential` without a successful evaluation** (guard against reintroducing the discarded-result pattern).

**Secret logging (H-03, H-04, L-09)**
- Post-pairing log-scraping test: capture the log buffer + `logLines` and assert no substring of `token`/`clientKey` appears (only lengths). 
- A lint/CI rule banning `privacy: .public` on any interpolation containing a URL, IP, token, or user-content name; banning token interpolation into `appendLog`.

**Credential storage (M-02, L-30, and to lock in the "solid" items)**
- Unit test asserting Keychain writes use `WhenUnlockedThisDeviceOnly` and are non-synchronizable (guards the verified-good state).
- Test that the token is **never** written to the App Group suite or watch `UserDefaults` (only routing metadata), and that the entertainment client key never enters `WidgetBridgeCredentials`/WCSession.
- Watch test: forget-all clears `wc_token`/`wc_bridge_ip` + App Group mirror; `credentials(for:)` returns nil afterward.

**Privacy manifest (M-03)**
- CI/build check that each shippable bundle (app, widget ext, watch app, watch ext) contains a `PrivacyInfo.xcprivacy` declaring the UserDefaults required-reason.

**Entertainment / DTLS (M-06, M-09, M-10, L-11, L-12)**

#### H-06 — [iOS] Trust-all TLS is also the transport for `behavior_instance` + scene writes (SAME delegate as H-01)
**File:** `HueHome/Core/Network/HueAPIClient.swift:723` (verdict: CONFIRMED)

#### M-14 — [iOS] App-driven effect loops fire unbounded high-frequency per-light PUTs with no mailbox/rate-limit and swallowed errors
**File:** `HueHome/Core/Effects/EffectEngine.swift:187` (verdict: CONFIRMED)
**Same class as M-08** (unbounded concurrent per-light fan-out, `try?`-swallowed errors, no mailbox), now in the Effects engine.

- **Defect:** `EffectLoops.setAll` (187) fans out one concurrent per-light PUT per light via `withTaskGroup`; `setOne` (202) issues `try? await api.setLightEffect(...)`, swallowing every error including 429. No latest-wins mailbox, no rate limiter, no stagger, no bounded queue. Strobe/party/thunderstorm drive `setAll` at high frequency: strobe at default 120 BPM ≈ ON+OFF ~4×/sec (~40 PUTs/sec for 10 lights), at its 480 BPM max ~16 setAll/sec (~160 PUTs/sec). Directly violates AGENTS.md "Hue API Rules" (latest-wins mailbox; no unlimited bridge writes; per-light REST rate-limited/batched/staggered) — rules the project already implements via `RestSender` in SyncModeEngine/StudioViewModel but this path bypasses.
- **Failure scenario:** Strobe at 300 BPM on a 10-light room emits ~120 PUTs/sec; the bridge (≈10 ZigBee cmds/sec) returns 429 and drops commands; `try?` hides them so no backoff occurs; the strobe stutters/desyncs and the bridge-wide throttle degrades other app features until the effect stops.
- **Fix:** Route effect writes through the shared latest-wins mailbox/`RestSender` with a per-bridge ~10 cmd/sec throttle; for same-color frames (strobe/thunderstorm flashes) collapse `setAll` into a single `grouped_light` PUT; at minimum stagger PUTs and stop swallowing errors so rate-limit failures back off. *(Partial mitigation today: `setAll` is awaited per frame so in-flight depth is bounded to N lights, and `start()` cancels the prior loop — the excessive per-frame **rate** is the core problem.)*

#### M-15 — [iOS] One-shot color and gradual effect-clear fan out unbounded concurrent per-light PUTs with swallowed errors
**File:** `HueHome/Core/ViewModels/EffectsViewModel.swift:301` (verdict: CONFIRMED)
**Same class as M-08 / M-14.**

- **Defect:** In `.oneShot`, after the `grouped_light` call, color is applied via `withTaskGroup` firing one concurrent `try? await api.setLightColor(id:)` per light (301-307). In `.gradual`, native effects are cleared via `withTaskGroup` firing `try? await api.setLightNativeEffect(id:, effect:"no_effect")` per light (353-357).
